# From blueprint pilot to a trained poker bot

## Objective and scope

Get a six-player, 100 BB, no-rake bot that reliably earns chips against the existing scripted style pool. That is the repository's v0.5 strength target. A stronger human-reference claim is a later v1.0 target. We will take ideas from Pluribus where they help, but the result matters more than reproducing its architecture.

The [first M4 pilot](reports/blueprint-pilot-v1.md) established legal play, exact resume, and a working arena. Its two iterations visited only 408 abstract information sets; at a fixed first preflop decision just 2/169 hand classes had trained entries. Its 332 MiB peak memory says little about a useful training run. The current trainer also copies the full regret table each iteration and compresses a checkpoint every iteration. Fix those scaling costs before using throughput from a longer run to choose hardware.

## Route to the first serious campaign

| Step | Work and exit decision |
| --- | --- |
| 1. Make the existing trainer scalable | Preserve a fixed policy during each six-role iteration without a full-table copy per iteration; checkpoint at a bounded wall-clock interval and on clean shutdown rather than every iteration. Keep atomic iteration publication, exact resume, legal-observation inference, and one focused recovery check. Add peak RSS, table growth, nodes/second, checkpoint time/size, disk use, and trained-versus-fallback decision counts. Before paying for many AWS CPUs, let workers traverse independent samples against the same frozen policy and combine their deltas at the iteration boundary; check that parallel and serial results remain valid. Do not start an architecture sweep. |
| 2. Start seed 1 on the M4 | Choose the six-player abstraction and sampling recipe intended for the long run. Run one capped, approximately one-hour slice with an **approximately 10 GiB process RSS ceiling** and a disk guard; leave memory for the OS and other work on the 16 GiB machine. Measure entry growth and throughput late in the slice, not only at startup. Save a resumable checkpoint and a small validation result. If the recipe stays fixed, this slice is the beginning of seed 1, not a disposable toy test. Weak poker results do not fail this step; illegal actions, non-finite values, failed recovery, or resource limits do. |
| 3. Measure paid scaling on RunPod | If projected peak RSS stays below roughly 10 GiB and finish time is acceptable, the M4 can continue training. Use RunPod for the next memory and worker-throughput measurement: 64 GB if the projected working set fits comfortably below about 45 GB, otherwise 128 GB. Continue the same seed if its recipe remains fixed. Measure actual work per dollar, total RSS across workers and any table copies, checkpoint size/time, and speedup as workers increase; a large AWS instance is useful only if the workload can use its cores. If the projection exceeds 128 GB, plan an AWS memory test or reduce the table before the full run. Do not pay for a GPU unless a later measured workload benefits from one. |
| 4. Choose and run the main campaign | AWS Spot is the likely long-run host, with `r7i.16xlarge` (64 vCPUs, 512 GiB) as a **candidate**, not the default regardless of measured need. Choose the smallest suitable instance and live-priced region using RunPod memory/work estimates; do one short AWS throughput check if 64-vCPU speed cannot be estimated from RunPod. Freeze the abstraction, sampling recipe, two independent training seeds, training-work target, maximum wall time, RSS/disk limits, checkpoint cadence, validation schedule, and **AWS spend ceiling** before the long run. Run enough fresh deals to cover common preflop and postflop decisions; do not declare an iteration count from the two-iteration pilot. Use sparse validation, for example at the halfway point and at the end, against the existing scripted pool. Do not stop or tune because an early win rate is negative. Retain every valid checkpoint and all failed-run evidence. |
| 5. Freeze and judge | Export the final checkpoint from each seed. Report trained/fallback coverage by street and position, card sensitivity, legal-action rate, BB/100 with uncertainty, total compute, peak RAM, and inference latency. If validation is promising, run **one fresh, predeclared confirmation** using the existing v0.5 rule: at least two independent training seeds, final checkpoints only, paired held-out deals, and multiplicity-adjusted lower confidence bounds above zero for each seed. No repeated attempts on the same final test. |
| 6. If strength is still poor | Diagnose the largest observed failure from coverage and hand traces. Make one targeted improvement and one comparable run. Likely candidates are better sampling/abstraction or observation-safe range-aware postflop search; more iterations of a structurally weak blueprint are not the default answer. Preserve the first campaign as a baseline. |

The first training campaign is complete when both declared seeds reach their capped work target, their frozen exports and reports are retained, and the strength result is stated honestly. It may fail the v0.5 gate; that result determines the next improvement. A training completion alone is not a claim of a very good player.

## RAM and spending rule

The M4 is the default for coding checks, recovery, the one-hour scaling slice, and any subsequent training that continues to fit. Run only one large seed process at a time on its 16 GiB RAM. A 10 GiB process ceiling is an initial guard, not evidence that a 10 GiB table will stay within it indefinitely; require a growth projection and watch the live RSS. A checkpoint must survive any guard stop.

The owner-reported RunPod console prices on 2026-09-24 are **$0.44/hour for 8 vCPU/64 GB** and **$0.88/hour for 16 vCPU/128 GB** in the 3 GHz memory-optimized tier, plus disk charges. Use the roughly $18 reported RunPod balance for bounded pre-campaign measurements, beginning with the M4 so paid tests answer a specific remaining question. For example, a $5 ceiling on one RunPod measurement buys at most about 11.4 or 5.7 pod-hours respectively, before storage. Check the live balance and complete pod price and set a ceiling for each test. The AWS campaign needs a separate budget and owner decision after we measure throughput; the RunPod balance does not fund it.

AWS [lists `r7i.16xlarge` as 64 vCPUs and 512 GiB](https://aws.amazon.com/ec2/instance-types/memory-optimized/), but [those 64 vCPUs are 32 physical cores with two threads each](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/cpu-options-supported-instances-values.html). The quoted **$1.13/hour Spot** rate is an unverified snapshot, not a campaign rate: [AWS says Spot prices vary by capacity and region](https://aws.amazon.com/ec2/spot/pricing/). The quoted $70–200 or $150–250 reproduction estimates are hypotheses, not our budget. Do not derive our runtime by dividing Pluribus's core-hours by 64 vCPUs, or assume a modern CPU makes our Python implementation faster than theirs. Use measured nodes or completed iterations per hour at each worker count, then calculate the two-seed budget from the selected AWS quote plus EBS, retained checkpoint storage, and evaluation.

For Spot, checkpoint at an interval whose recomputation cost is acceptable, write atomically to persistent storage, and verify that a fresh instance can load the latest retained checkpoint. [AWS gives roughly two minutes of interruption notice](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-best-practices.html), which is too little to rely on for an unmeasured large-table save. [EBS can persist after instance termination](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-lifecycle.html); configure that behavior deliberately and account for its continuing charges. An interruption resumes from the last durable checkpoint within the frozen work and spend caps.

The [Pluribus paper](https://noambrown.github.io/papers/19-Science-Superhuman.pdf) reports about **$144 in 2019 cloud spot prices** for its blueprint: eight days, 12,400 CPU core-hours on a 64-core server, and less than 512 GB training RAM. Its **128 GB** limit is for playing with the compressed blueprint, not its training RAM. Pluribus then used real-time search after the first betting round, so its final playing strength cannot be attributed to blueprint training alone. Those figures do not price our Python trainer or guarantee that a 16-vCPU/128-GB rental can reproduce Pluribus on the same schedule. The budget should be based on our measured run, with storage and evaluation included.

## Deliberately few gates

One focused recovery check, one useful M4 scaling slice, a bounded RunPod memory/parallelism measurement, at most one short AWS throughput check if needed, two full seeds, sparse validation, and one fresh confirmation if the policies warrant it. Correctness and resource failures stop the run immediately. A negative interim poker estimate does not trigger another sequence of tiny tuning runs. The final strength gate remains firm because otherwise we cannot tell whether training produced a decent bot.
